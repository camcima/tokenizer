# PCI DSS mapping

This page is for a Qualified Security Assessor (QSA), or for whoever prepares the evidence for one. For each of the twelve principal requirements of PCI DSS v4.x it shows where the requirement is addressed by this repository's code and tests, where by the documented deployment, and what is not addressed here and remains with the organisation. It is a map for finding evidence, not a compliance claim. The plain-language introduction to PCI DSS is in [README §3](../../README.md#3-pci-dss-in-plain-terms).

## Scoping

### What the vault handles

| Data element | How the vault treats it | Where it exists |
|---|---|---|
| PAN | Cardholder data. | In TLS from the browser; in vault memory for one request; sealed with AES-256-GCM in `vault.cards.ciphertext`; in the provider request inside TLS. Never logged. No vault endpoint returns it; a provider echo of it in a `/proxy` response is masked only in the forms listed under [what the platform receives](#what-the-platform-receives). |
| Expiry, cardholder name | Encrypted together with the PAN in the same record (`card.go`, `card`). | Inside the ciphertext. The expiry is also returned by `/tokenize`; the name is returned only inside the signed receipt, to the browser that supplied it. |
| CVV | Sensitive authentication data. Never stored. | Vault memory only (`card.go`, `cvvCache`): single use, expires 15 minutes after tokenization, expired entries removed by a sweep every 60 s, bytes overwritten on removal (best effort). A provider 2xx on `/proxy` drops it only on the instance that handled the call, so a CVV cached on another instance can stay in memory until it expires, about 16 minutes after tokenization at worst ([residual risks](threat-model.md#residual-risks)). Not part of the encrypted record, the database or any log. |
| Last four digits | Truncated data. | Stored in clear in `vault.cards.last4` (`CHECK (last4 ~ '^[0-9]{4}$')`, `schema.sql`); returned by `/tokenize` and in the receipt. |
| BIN | Truncated data. 8 digits for a 16-digit PAN, 6 for every other length (`receipt.go`, `cardBIN`). | Only inside the signed receipt. The vault does not store it. |
| Token | Not derived from the PAN. | `tok_` + 32 hex characters from 16 bytes of `crypto/rand` (`card.go`, `newToken`); no mathematical relation to the card, and no vault endpoint maps it back to card data. |
| DEKs, key-encryption key | Cryptographic keys protecting cardholder data. | DEKs wrapped in `vault.deks` and unwrapped in vault memory; the key-encryption key in Cloud KMS (HSM) in a separate project. |

The vault never produces a hash of the PAN.

### Why truncated data is handled differently

Truncation removes digits permanently: unlike a ciphertext, a truncated number cannot be turned back into the PAN with a key. The vault limits the digits it releases so that, combined, the BIN and the last four always leave digits hidden. For a 16-digit PAN the receipt carries the first 8 and last 4, which leaves 4 hidden. For every other length it carries the first 6, the conservative choice, because the vault has no card-brand confirmation for a longer prefix at those lengths; even a 13-digit PAN keeps 3 digits hidden. `TestReceiptBIN` covers the rule.

That is why the platform may receive these facts while it never receives the PAN. [README §6.2](../../README.md#62-the-signed-receipt) states the rules the platform must follow with them: show customers only the last four, never store a hash of the PAN next to truncated data, and derive brand and issuer from its own BIN data.

### What the platform receives

- From `/tokenize`, through the browser: `token`, `last4`, `exp_month`, `exp_year` and `receipt` (token, BIN, last4, expiry, optional name and issue time, Ed25519-signed).
- From `/proxy`: the provider's status, `Content-Type` and body, with this card's number masked as `****` + last four when it appears as plain digits or grouped in fours with single spaces or hyphens (`outbound.go`, `maskPAN`). Other groupings and every other field a provider returns (a cardholder name, a provider token, an error message) are relayed as is.
- Single-use hand-off tokens created by catalog endpoints (Stripe `tok_…` today), which the platform uses with its own provider keys.

The vault itself never returns a full PAN or a CVV. A provider response is relayed as is apart from the masking above, so whether a provider echo of other card data (a CVV, an expiry, an unmasked grouping of the PAN) can reach the platform depends on the provider's behaviour and on the catalog review of each endpoint's documented responses.

### Who decides scope

**The assessor decides the scope of the assessment, on the basis of the actual deployment and the segmentation evidence. This document does not.** The design intent, as the README puts it, is to keep the platform's back end out of scope "subject to the assessor's scoping" ([README §5](../../README.md#5-how-the-vault-shrinks-our-scope)); whether it is also depends on its segmentation from the CDE. Points an assessor will want to examine:

- The vault, its Cloud SQL instance, Secret Manager, the KMS key and the projects that contain them hold or protect cardholder data; the design intends them to form the CDE.
- The platform opens mTLS connections to the internal listener and holds the session HMAC key. How those connections and keys are classified is a scoping question for the assessor.
- The checkout page that hosts the card form, and the systems that serve it, handle the card in the browser and are usually still in a reduced scope ([README §5](../../README.md#5-how-the-vault-shrinks-our-scope)).
- The pipeline that builds and deploys the vault image, and the infrastructure configuration that sets its network and IAM controls, can affect the CDE's security.

## Artefacts an assessor can ask for

- **The source at a commit and the image built from it.** Builds are reproducible, so the image digest identifies the build inputs (`go.mod`, `go.sum`, the `*.go` files, `catalog.json` and `vendor/`, as copied by the `Dockerfile`), and through them the reviewed source and catalog (`make image-repro`; the Image workflow keeps the digest as a build artifact).
- **CI logs** from the four workflows: CI (`make ci`, commit checks), Integration (`make itest`, `make stripe-mock-test`, `make cover-check`), Image (`make image-repro`, `make image`) and Fuzz (pull-request and nightly runs).
- **The tests named on this page**, in the `*_test.go` files, and the saved fuzz inputs under `testdata/fuzz/`.
- **`schema.sql`**, the only SQL, with the role grants.
- **`catalog.json`, `egress-hosts.dev.txt` and `egress-hosts.prod.txt`**, and the pull requests that changed them with their review checklists.
- **`docs/risk-register.md`.**
- **This documentation set**, including the [threat model](threat-model.md) and [architecture](architecture.md).
- **Boot logs** of a running instance, which show the loaded DEK versions and the receipt public key, and never a secret.

## What is not evidence

- **The README is not a Report on Compliance or an Attestation of Compliance**, and neither is this page. They describe the design and its intent.
- **Tests prove what the code does, not how it is deployed.** That the deployment matches column (b) needs evidence from the deployment: the infrastructure configuration, IAM and firewall settings, cloud audit logs and the deploy pipeline's records.
- **`stripe-mock` is not a provider certification.** It checks request shapes; the provider's own sandbox verification and documentation are recorded in the catalog pull request.
- **A statement that data "is not cardholder data"** in any of these documents is the design's position. The assessor makes that determination.
